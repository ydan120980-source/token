# 未报告缓存写入的计价与 Antigravity 模型配对（2026-10-17）

项目负责人发现大量模型因来源没有报告缓存写入而无法计费。`feat/package-and-ui-polish` 上为此加了三项规则，复核后保留一项、修正一项、撤回两项。本记录是修正后的语义，实现以该分支的提交为准。

## 缓存写入未报告

来源没有缓存写入字段时，按计费服务商（价格的 `billingProvider` 或记录的服务商，路由模型按模型名识别）处理：

| 情况 | 结果 |
|---|---|
| 价格中缓存写入为 0（目录或手动） | 写入不产生费用，按精确计价。手动价格填 0 是用户声明供应商不收写入费 |
| Codex 或 Antigravity，服务商为 OpenAI、DeepSeek、Google，目录没有写入价 | 这些服务商不单独收取缓存写入费，按 0 计价（判断依据是公开计价方式，本次没有联网核对） |
| Codex 或 Antigravity，目录有大于 0 的写入价（含 Antigravity 上的 Anthropic 模型） | 给出区间：下限为没有写入，上限为全部未缓存输入都是写入。依据是这两个来源把输入全部计入未缓存、缓存读取、输出三个互不重叠的桶 |
| Antigravity 上的 Anthropic 模型，目录没有写入价 | 未知（`missing-cacheWrite`）。Anthropic 对缓存写入收费，不能按免费算 |
| 其他来源 | 未知 |

撤回：Antigravity 上的 Anthropic 模型缺写入价时按免费计价。

## 撤回：由总量推断缓存读取为 0

规则是"总量等于未缓存输入加输出时，缓存读取为 0"。但来源没有缓存读取字段时，总量本来就是由已报告的各桶相加得出的（`src/m1/normalize.js`），这个等式恒成立。所以它并没有推断出什么，而是把每一条未报告的缓存读取都填成了 0，违反"未知不填 0"。撤回后，这类记录继续列在"未计入估算的用量"里，原因为来源未报告缓存读取。

## Antigravity 模型配对

- 保留：能解码但没有模型 ID 的 `gen_metadata` 行视为失败的生成尝试（如 429），不参与配对。无法解码的行保留位置，只有对应的那次调用记为未知，后面的配对不会错位。失败尝试在 transcript 中没有对应调用：这是根据分支提交说明得出的判断，没有用真实样本核对（真实来源只能由项目负责人通过 `validate:local` 核对）。
- 撤回：调用数比模型数多 1～3 条，且已提交的模型都相同时，多出的调用继承这个模型。这里无法判断对话是否真的还在进行，最后一轮也可能换了模型；而且进行中的调用不需要推断：对话库变化会触发重读（`src/m1/sources.js` 的来源戳记包含对话库及其 WAL），库写入后下一次采集就能按位置配对。所以继承实际只会作用于永远对不上的对话，正是最容易配错的情况。

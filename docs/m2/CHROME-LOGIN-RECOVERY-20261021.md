# Chrome 登录与闪退恢复 — 2026-10-21

用户报告：除 OpenCode 外的额度登录会闪退，要求改用本机 Chrome。用户进一步明确选择「只打开日常 Chrome 标签页，接受手动提供凭据」，没有选择独立 Chrome 自动会话读取。

Windows Application 事件 1000/1001 记录了此前多个发布代次的原生崩溃，包括 codexbar-login-20261020-final。重复签名为 Electron 43.4.0、0xc0000005、offset 0x2b18363。没有读取可能包含凭据的内存转储；这些记录证明原生崩溃存在，不能单凭偏移确定具体原生函数。旧版合成 HTTPS/UI 测试不能覆盖真实网站的浏览器行为，因此不作为真实登录成功证据。

## 交互与边界

- 七个网站来源统一只打开固定官网 HTTPS 地址，Chrome 使用 `--new-tab` 与独立参数、无 shell；没有内置登录窗口，也不通过默认浏览器意外转向其他应用。找不到 Chrome 或启动失败时返回可重试错误，不退出应用。
- 不带 profile、debugging、扩展或页面注入开关，不读取 Chrome 文件、标签页或会话。网站使用用户日常 Chrome 的正常登录；登录后用户返回连接表单，手动提供所需 Cookie 或 Token。页面打开不创建连接、不查询额度、不表示授权完成。
- DeepSeek 平台使用 userToken 值；Cookie 来源遵守既有字段规范。WorkBuddy 必须同时提供该请求的 User-Agent。Claude／OpenCode 可明确指定多组织／工作区 ID，后端仍验证其属于当前会话。
- 手动凭据可选择 Windows safeStorage/DPAPI 保持连接，先验证额度再提交；不勾选则仅内存。只保存必要字段，既有 vault 与连接缓存向后兼容；重启恢复不联网，显式刷新，失效清除，移除删除。
- Codex 使用官方 CLI 返回的授权地址，明确交给 Chrome；浏览器启动失败会取消本次授权。Claude／Gemini／Antigravity 保留官方 CLI 的外部授权与手动回填流程，不引入嵌入式页面，也不修改系统默认浏览器。
- 使用现有样式、组件与设计 token；无 CSS/设计 token 修改。GitHub 和真实账号自动验收不在本轮范围。

## 验证

执行结果另见 RESULTS-CHROME-LOGIN-20261021.md。测试使用合成凭据与独立 home/usage/quota。普通 Chrome 派发的参数、失败、重试与 UI 手动连接分别覆盖；不把 stub 派发或合成服务响应写成真实 Chrome 登录／真实额度验收。原生崩溃的精确栈仍未定位；本轮移除了其原有内置网页登录执行路径。

打包首轮外观套件另触发原生崩溃，签名为 0xc0000005、offset 0x6966498，区别于上述旧版登录签名。当前 Electron 类型定义要求 `menu.closePopup(window?: BaseWindow)`；旧测试传入数字窗口 ID，并且没有等待菜单打开。测试改为传窗口对象、等待 `menu-will-show`／`menu-will-close`，同一打包程序在 100%／150% 下复跑通过。没有修改产品菜单实现或撤销非法操作拒绝断言；保留首轮失败证据。

用户随后明确要求真实 Cookie 验收，并选择「现在逐项验收可用账号」。本轮可启动独立应用数据目录的可见打包程序，由用户在本地表单录入凭据、显式连接查询；只观察脱敏连接状态、测量覆盖与更新时间。暂停本地用量采集和价格自动同步，不读取既有 Chrome 会话，也不在聊天接收凭据。每个账号的实际结果另记，未提供的账号仍属未验收。

# 显示采集失败的原因（2026-10-22）

## 背景

GPT 在 `src/m1/collection-diagnostic.js` 里加了采集失败诊断 `{stage, category, reason}`。它经由 `Service.get().diagnostic` 和 `usage:get` 传到渲染层，但界面上一直没有用到。以前采集失败时，侧栏顶部只显示"采集没有完成"，要悬停才看得到 `COLLECTION_FAILED` 这样的错误代码：用户不知道原因，也不知道去哪里处理。

所有者确认按以下方案做：把诊断并入来源管理的"需要处理"列表，不新增区块。

## 实现（只改渲染层）

- **"需要处理"列表里的实时条目**：最近一次采集失败时，`insights-ui.js` 在列表最前面加一条，归入"来源"类别。条目用一句话写清三件事：
  - 原因：按 `category`/`reason` 译成中文，例如 `EACCES` 显示为"没有访问权限"，`NATIVE_BINARY_MISMATCH` 显示为"统计组件校验不一致，已拒绝运行"，`COLLECTION_TIMEOUT` 显示为"采集超时"；
  - 环节：由 `stage` 决定，例如"扫描来源文件"、"统计组件核对"；
  - 处理建议：一句话，例如"检查该位置的访问权限后重新检查"、"重新安装本应用后再试"。
- **错误代码放在悬停提示里**：错误代码和原因代码在标题的悬停提示中。`UNKNOWN`、`CONTROLLED_ERROR` 这类占位代码不显示。
- **如实说明原因**：
  - `category: 'unknown'` 显示"原因未知"，不猜测具体原因；
  - 没有诊断（`diagnostic: null`）时显示"原因未报告"，也不显示环节；
  - 受控错误（`CONTROLLED_ERROR`）用 `state.error` 中的公开代码说明原因，例如"读取位置不被允许"；没有对应文案时显示"采集遇到已识别的问题"。
- **不点名来源**：诊断是全局的，不对应某个具体来源，所以条目不写来源名称，按钮是"重新检查"（与页头的重新检查是同一个动作），不是"查看来源"。
- **不能标记"已知悉"**：这个条目反映的是当前状态，不能标为已知悉；下一次采集完成后它自动消失。
- **侧栏顶部的提示**：提示改为"最近采集没有完成 · 查看原因"。"查看原因"是一个按钮，点了会打开来源管理，并聚焦到"需要处理"。提示只在文字变化时才重建，所以定时更新不会抢走键盘焦点。
- **来源管理的说明行**：原句"可重新检查并采集"改为"原因见下方'需要处理'"，不再和条目重复。
- **数据传递**：`preview.js` 新增 `usageData.collection()`；当错误、诊断或采集中状态变化时，派发 `usage-collection` 事件。后端、IPC 和诊断字段都没有改动。

## 测试

新增 `scripts/m1/collection-diagnostic-ui-test.js`：
- **注入方式**：在主进程里包装真实的 `usage:get` 处理函数，并入合成的 `{error, diagnostic}`。并入的值与 `Service.get()` 返回的形状一致，已经过 `sanitize`。
- **覆盖六种情况**：os（EACCES）、native（NATIVE_BINARY_MISMATCH）、受控错误（SOURCE_PATH_REJECTED）、超时（COLLECTION_TIMEOUT）、unknown、无诊断。每种都核对四点：原因、环节和处理建议的文案；悬停提示里的代码；条目没有"已知悉"按钮；条目排在列表最前。
- **交互**：
  - 用键盘聚焦"查看原因"后，相同内容的更新不会让焦点丢失；按 Enter 会打开来源管理并聚焦标题；
  - "重新检查"会触发 `#sourceRefresh`；
  - 采集恢复后，条目和侧栏提示都会消失；
  - 页面没有报错。
- **截图**：浅色和深色下各截了列表和侧栏提示，另有一张整窗截图。

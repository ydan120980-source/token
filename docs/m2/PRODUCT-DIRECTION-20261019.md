# 公开用户与 GitHub 项目状态方向（2026-10-19）

所有者明确并要求记录：产品首先面向公开用户；后续主线为 GitHub 账号绑定、远端 GitHub 项目状态监控及部分 Git 功能。近期优先让额度监控与来源管理对齐。配置健康检查、MCP/hooks/skills 审计和 DIY 不再是当前优先方向；已有实现保留，不据旧路线自动推进后续阶段。

## 推进顺序

1. 额度与来源对齐：统一来源能力、账号连接、读取结果和数据新鲜度的表达，保留各自独立状态；有本地用量不等于已接入账号额度。真实额度仍仅 Codex，不虚构其他提供商额度，不读取其认证或配置。
2. GitHub 只读项目监控：明确绑定账号、用户选择仓库、最近提交、PR 状态、Actions/检查状态和最近成功更新时间，先形成完整闭环。
3. 本地 Git 只读状态：用户选择本地仓库并明确关联远端项目，显示分支、工作区改动、已知领先/落后及远端数据更新时间。
4. 经过独立范围决定再增加有限 Git 写操作，提供预览、显式提交和失败恢复；不默认授予全部仓库或写权限。
5. 配置健康、DIY 等扩展以后再根据核心用户需求评估。

后续额度研究补充见 [额度可行性与生命周期研究](QUOTA-FEASIBILITY-RESEARCH-20261019.md)：所有者要求核对不同来源的实际额度读取、会员/积分到期及现成实现，并提供 Orca、Todos、XD Pool、AxonHub。研究建议先完善多池/积分/资格合同，再优先验证 Antigravity 官方 CLI；WorkBuddy 官方个人积分接口的授权条件与到期明细另行评估。该建议不把尚未接入的来源标为支持，也不自动批准新认证读路径、服务端、模型探针或多账号转发。

公开发行需要贯穿首次使用、连接/断开、错误恢复、访问范围说明及安装升级保留数据的验收。首批可以聚焦使用 AI 编程并维护 GitHub 项目的个人开发者及小团队；这是产品设计选择，不把“公开发行”解释为所有功能对所有人同时适用。

## 当前批准的实现增量

本轮在 main ac6d46e 基础上实施额度/来源能力与状态对齐，并提交 GitHub 首版对象/连接/权限合同。用既有额度页与来源页，不增加独立工作台，不重做获批视觉。需要明确支持/未接入/未确认、连接情况、缓存和最近成功；来源停用不能暗中断开账号，账号断开不能删除来源历史。动态个人来源只展示其真实用量能力。

本轮不实现 GitHub 登录、远端轮询、真实账号接入、新品牌额度适配、Git 命令或通知/后台常驻，不启动配置读取阶段。先使用合成数据验证，按项目门禁复核并本地合入；不创建正式发布代次或替换运行包。后续每项在其阶段细化接口和验收。

## GitHub 首版合同

- 连接（用户授权与失效/撤销）、选定仓库、仓库状态是独立对象；选仓库不自动扫描会话路径或本地磁盘。GitHub 身份和仓库访问须分别确认。
- 每项状态携带观察时间、最近成功、读取范围和受控错误。权限不足、被限流、离线或旧缓存不能显示为“项目正常”。PR/CI 状态采用 GitHub 返回的明确状态，不从数量猜测健康。
- 优先评估 GitHub App 的细粒度仓库权限；桌面授权与凭据保存方案在接入前确定，不把发布者 client_secret 或 App 私钥放入安装包，不沿用开发机凭据作为产品授权。官方依据：[GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps)、[权限](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)。
- 首版只读选定仓库的元数据、最近提交、PR 与 Actions/检查状态；不下载代码、工作流日志或附件，不提供合并、重跑 CI、写 Issue/PR、推送或发布动作。接口核对：[workflow runs](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository)。
- 优先有限轮询、条件请求、请求合并及退避，尊重 GitHub 的限流响应；第一版不要求公开 webhook 服务。[REST 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)。GitHub 请求限额独立于 Agent 账号额度。
- GitHub 产品能力与本项目开发仓库的同步政策是两回事：本仓库继续 local-only，不 push、不打开 PR，origin/main 保持既有基线，恢复同步另行决定。

## 首个增量的实现合同

SourceConnectionsV1 从已保存的内存状态构建，逐来源返回用量状态、额度能力、连接计数、待登录/读取失败/重复连接计数、fresh/stale/cached/missing 覆盖以及成功时间范围。只读接口 usage:connections 不发起扫描、采集、额度请求或登录；不返回账号 ID、备注、计划、窗口或认证信息，也不接入 MCP 查询。

fresh 要求连接已验证、最近成功不超过十分钟且没有已过重置时间的窗口；刚启动的缓存仍待验证，过期窗口不能推断已补充，未来异常时间不标成刚更新。多连接逐项计数，不加总额度；一项成功不把其他连接标为最新。来源停用与账号断开各自独立，个人来源和已移除的个人来源保留用量能力说明。

额度页增加与来源目录一致的列表，来源页对应行显示额度能力与连接状态，双方有明确导航。概览读取失败保留旧视图并标记待检查，支持重试；没有成功概览时连接数为未知。界面沿用来源行、字号间距 tokens 和现有账号 sheet；没有独立工作台或视觉重做。

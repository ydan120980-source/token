## 现在的内存落在哪

事实：下表是我从你的原始证据算的（`token-evidence/perf-continuation-20261104/continuation-closeout/memory/codex-cooperative-*`，300 Hz / 125%，合并前，各一轮）。单位 MiB，“工作集 / 提交”。

| 负载 | 峰值合计 | 主进程 | 渲染 | GPU | 结束时合计 | 主进程 | 渲染 | GPU |
|---|---|---|---|---|---|---|---|---|
| 文件扫描 | 497 / 886 | 217 / 237 | 185 / 205 | 88 / 433 | 330 / 692 | 92 / 113 | 156 / 173 | 75 / 393 |
| 对比 | 475 / 849 | 190 / 213 | 193 / 210 | 86 / 414 | 330 / 681 | 92 / 112 | 160 / 176 | 71 / 381 |
| 三栏 | 440 / 692 | 163 / 189 | 190 / 210 | 79 / 281 | 367 / 605 | 120 / 137 | 166 / 182 | 74 / 273 |
| 两栏 | 428 / 701 | 165 / 191 | 179 / 200 | 77 / 298 | 359 / 623 | 120 / 141 | 160 / 177 | 72 / 292 |
| 全部列表 | 389 / 629 | 162 / 180 | 166 / 183 | 55 / 254 | 269 / 508 | 89 / 110 | 118 / 138 | 54 / 248 |

由此得到（我的判断）：

1. **扫描的余量只有约 1.3 MiB，而瞬时增量几乎都在主进程：** 比结束时多约 125 MiB，渲染只多约 29，GPU 只多约 13。Worker 线程算在主进程里。
2. **私有提交的差距几乎都在 GPU：** 工作集 55–88，提交 254–433。去掉 GPU 这部分，其余都在 500 以下。
3. **GPU 提交不随栏数涨：** 三栏 281，扫描和对比却有 430 左右。说明不是“栏多”，而是某一步或某个表面（推测，未验证）。
4. **闲置仍高：** 看完后停在 270–370，托盘隐藏窗口也一样，因为渲染进程还在。

## 建议的杠杆，按优先级

每一项先做归因再改。除第 1 项外都是推测，要用测量证伪。

1. **扫描和对比的 Worker 峰值。** `fileHistory`、`search`、`toolUse`、`facts` 都走 `src/m1/transcript-tasks.js`；`HEAP_BUDGET` 32 MiB 只在回答之后才退役，Worker 没有 `resourceLimits`。可以试：
   - 按行流式读，先用子串过滤（路径、查询词）再 `JSON.parse`，不进 Builder。
   - `fileHistory` 和 `toolUse` 只需要编辑工具行，`facts` 只需要计数。
   - 一批文件中途超预算就退役 Worker 再继续。
   - 在 Worker 里记 `process.memoryUsage()` 的 `heapUsed`、`external`、`arrayBuffers`：PDH 分不开线程，Buffer 也不在堆里。
2. **定位 GPU 提交跳变的那一步。** 用已有采样器按步骤打点，看 254 到 433 发生在哪。重点看合成层：`backdrop-filter`、`will-change`、常驻 transform、滚动容器、对比和文件扫描各自的面板。
3. **隐藏窗口时释放渲染进程。** `src/quota/desktop-shell.js:109` 现在只是 `window.hide()`。托盘小卡片和额度提醒都不依赖主窗口，所以可以隐藏若干分钟后销毁窗口，点开时重建。这可能是闲置收益最大的一项。**代价是重新打开变慢，要报实测时间，默认值请所有者决定。**
4. **隐藏页面常驻。** `ui/src/app.tsx` 的六个页面用 `hidden` 一直挂载，图表和投影都留着。试试隐藏一段时间后卸载重子树（状态本来就在 host 里），同时看切页耗时不能变差。
5. **这轮 UI 新增的潜在开销，都没有测：**
   - `AgentInventoryService.plan()` 在主进程同步读文件（`tree()`，每项上限 4 MB），项目多时会卡主线程。
   - Agent 管理的行没有虚拟化，上限 1000 项；kit 里有 `windowed-list`。
   - 文件栏平铺和树形都一次画最多 200 行。
6. **代码分割最后做。** 现在是一个 1.35 MB 的 bundle，`tests/m1/ui-bundle.test.js` 也要求单一 bundle，要改得先问所有者。

已经试过没有收益的，不要重复：升级 Electron（43.8.7、45.2.2）、GPU 后端、Graphite、V8 8/20、整页 `useDeferredValue`、通用测量抽象、Worker 跨记录复用、复制整树字符串。

## 怎么走得更快（我的判断）

你的结果是实在的（采集 2.3–3.5×，五类工作集都在 500 以下），慢主要在流程：

- **早合并，合小块。** 分支长期不合，main 一动回执就作废，这是最大的返工来源。每个有收益的杠杆单独过门禁合入，当天合。
- **先归因，再试。** 上一轮不少时间花在全局开关上，都没有收益。先看上表，只动占比最大的那块。
- **两档测量。** 迭代时只跑受影响的那一个负载，不做指纹和回执；合入前才跑五类。
- **给试验设上限。** 一个杠杆两轮内省不到 20 MiB 就记一行放弃，换下一个。
- **记录减量。** 每次合入一张表：负载、前后峰值、闲置、长任务、没做什么。过程细节放提交说明。

建议目标（待所有者确认，当前正式目标仍是 300–500 MiB）：

| 指标 | 建议 |
|---|---|
| 五类负载工作集峰值 | 都不超过 450 MiB，留出波动余量 |
| 看完后闲置 | 不超过 250 MiB |
| 隐藏到托盘（如做第 3 项） | 不超过 120 MiB |
| 私有提交 | 单列汇报，不作为门槛，除非所有者要求 |
| 交互 | 切页和离开阅读页到下一帧 100 ms 内；不追求零长任务（现在 50–66 ms 刚过阈值） |
